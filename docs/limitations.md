# Limitations

> Honest documentation of what doesn't work, what's hard, and what you need to plan around. Every limitation includes its mitigation strategy.

---

## 🔴 Critical Limitations

### Copilot PAT Requirement

**The single biggest operational dependency.**

GitHub Apps cannot hold Copilot licenses. You **must** have a Copilot-licensed user generate a Personal Access Token (PAT) and upload it to Key Vault. This creates several operational concerns:

- **PAT expiration**: When the PAT expires, all agent runs fail silently (Copilot CLI returns a non-zero exit code, and the fallback work artifact is created instead of real code changes).
- **License dependency**: If the PAT owner loses their Copilot license (seat removed, org change, subscription lapse), all agent runs fail.
- **Token scope**: The PAT needs at minimum the `copilot` scope. Broader scopes increase blast radius.
- **Rotation burden**: Someone must remember to rotate the PAT before it expires.

**Mitigation**:
- Use a **dedicated service account** with a Copilot Business license. This decouples the PAT from any individual developer.
- Set a **calendar reminder** for PAT rotation (90 days before expiry).
- Monitor the `COPILOT_EXIT` code in container logs — non-zero indicates a likely auth failure.
- Store the PAT in Key Vault with an **expiration date** so Azure can alert you.

```bash
# Upload with expiration tracking
az keyvault secret set \
  --vault-name "kv-squad-XXXX" \
  --name "copilot-pat" \
  --value "<PAT>" \
  --expires "2027-01-01T00:00:00Z"
```

### Container Runtime Limit

Azure Container App Jobs have a configurable timeout, defaulting to **1800 seconds (30 minutes)**.

- Complex issues with large codebases may timeout during the Copilot CLI phase.
- The container is hard-killed at timeout — no graceful shutdown, no partial PR.
- The message has already been deleted from the queue, so the work is lost.

**Mitigation**:
- Increase `agent_job_config.timeout_seconds` in `terraform.tfvars` (max depends on ACA limits).
- Break complex issues into smaller, focused sub-issues.
- Most Copilot CLI runs complete in **under 5 minutes** for typical code changes.
- Monitor execution duration in Log Analytics to identify patterns.

## 🟡 Operational Limitations

### No Persistent Workspace

Each container starts completely fresh. There is no shared filesystem, no cached dependencies, no workspace state between runs.

- Every run clones the entire repository from scratch.
- Large repositories (>1GB) increase startup time significantly.
- Build caches (node_modules, .gradle, .cargo) are not preserved.

**Why this is intentional**: Persistent storage adds cost (Azure Files, Managed Disks) and introduces failure modes (stale cache, corrupted workspace, leftover state from failed runs). Ephemeral containers guarantee isolation.

**State that persists**:
- Git (decisions.md, history.md flow through PRs → merge → future runs read them)
- Key Vault (secrets survive container lifecycle)
- Storage Queue (messages survive until processed or TTL expires)

---

### Manual Secret Management

Two secrets must be uploaded to Key Vault out of band after deployment, regardless of whether you use Terraform or Bicep with `azd`:

1. **GitHub App private key** (PEM file) — generated when creating the GitHub App
2. **Copilot PAT** — generated by a Copilot-licensed user

The IaC templates do not manage these secret values because Terraform state or deployment history could expose them. Keep the values in your secure secret process and upload them with `az keyvault secret set`.

**Mitigation**:
- Store the PEM file in a secure vault (1Password, LastPass, Azure secondary Key Vault).
- Document the rotation procedure for your team.
- Use `az keyvault secret set` with `--file` (PEM) or `--value` (PAT).

```bash
# Upload PEM
az keyvault secret set --vault-name "kv-squad-XXXX" \
  --name "github-app-private-key" --file ./private-key.pem

# Upload PAT
az keyvault secret set --vault-name "kv-squad-XXXX" \
  --name "copilot-pat" --value "ghp_XXXX..."
```

### GitHub Actions variables outside Bicep

Bicep cannot manage GitHub repository variables because GitHub is outside the Azure Resource Manager control plane.

The Bicep and `azd` path handles this with a post-provision `gh` CLI hook that sets:

- `SQUAD_AZURE_CLIENT_ID`
- `SQUAD_AZURE_TENANT_ID`
- `SQUAD_AZURE_SUBSCRIPTION_ID`
- `SQUAD_STORAGE_ACCOUNT`
- `SQUAD_QUEUE_NAME`

**Mitigation**:
- Run `gh auth login` before `azd up`.
- Ensure the authenticated GitHub account can edit Actions variables on each target repo.
- If the hook fails, rerun `azd provision` after fixing `gh` authentication or set the variables manually.

### Local Terraform State

The Terraform path uses local state. This template does not configure an Azure Storage remote backend because remote state design, locking, and access control are outside the scope of issue #9.

**Implications**:
- Keep the local state file secure.
- Do not commit `.tfstate` files.
- Coordinate Terraform runs so two people do not apply from different local states at the same time.

**Mitigation**:
- For team production use, add a remote backend before broad adoption.
- Use the Bicep and `azd` path if you prefer ARM idempotency without Terraform state.

### Docker Hub Rate Limits

The Dockerfile references base images cached in ACR, but the **initial import** requires pulling from Docker Hub.

- Anonymous pulls: 100 per 6 hours per IP
- Authenticated pulls: 200 per 6 hours
- `az acr build` needs the ACR-cached images to exist before the build starts

**Mitigation**:
- Import base images **once** before the first `az acr build`:
  ```bash
  az acr import --name <acr> --source docker.io/library/golang:1.23.4-bookworm \
    --image base/golang:1.23.4-bookworm
  az acr import --name <acr> --source docker.io/library/debian:bookworm-20240701-slim \
    --image base/debian:bookworm-20240701-slim
  ```
- The `azd` post-provision hook imports these base images automatically.
- When you build manually, pass `--build-arg BASE_ACR_HOST=<your-acr-login-server>/` to `az acr build` so the Dockerfile `FROM` lines resolve to your ACR instead of the default bootstrap ACR.
- After import and the build-argument override, Docker Hub is never contacted.
- Re-import when upgrading base image versions.

### Single Queue

All target repositories share one Azure Storage Queue (`squad-work-queue`). There is no per-repo queue isolation.

- High volume from one repo could create queue contention for all repos.
- No priority routing — messages are processed FIFO.
- A poison message (malformed JSON) will fail one container but won't block others (since the container deletes the message before processing).

**Mitigation**:
- For most teams, queue throughput is not a bottleneck (Azure Storage Queue handles thousands of messages per second).
- If isolation is needed, deploy separate Storage Accounts with separate queues and separate KEDA triggers.
- The `maxExecutions` setting (default 10) caps parallel containers, providing natural backpressure.

### No Retry on Copilot Failure

If Copilot CLI fails (exit code ≠ 0), the container creates a **work artifact** (`.squad-work/issue-N.md`) and creates the PR with a diagnostic note. It does **not**:

- Re-enqueue the message for retry
- Start a new container for the same issue
- Notify the user via any channel other than the PR body

**Why**: Automatic retry would likely fail again with the same error (bad prompt, auth issue, rate limit). The work artifact preserves context so a human can investigate.

**Mitigation**:
- Check the PR body's "Pipeline Status" table — Copilot shows `⚠️ fallback` if it failed.
- Check `.squad-work/issue-N.md` in the PR for Copilot's last 50 lines of output.
- Fix the root cause (expired PAT, malformed issue body), remove the `squad:queued` label, and re-label with `squad:{agent-name}` to retry.

### OIDC Federated Credential per Repo

Each target repository needs its own **federated identity credential** on the UAMI. This is because GitHub Actions OIDC tokens include the repo name in the `sub` claim.

```
subject: repo:owner/repo:ref:refs/heads/main
```

**Implications**:
- Adding a new target repo requires a Terraform change (`target_repos` list) and `terraform apply`.
- Each federated credential is a separate Azure resource (there's a limit of 20 per managed identity by default).

**Mitigation**:
- Add repos to `var.target_repos` in `terraform.tfvars` and run `terraform apply`.
- For large-scale deployments, use a broader subject filter (e.g., `repo:org/*:ref:refs/heads/main`) — requires custom OIDC configuration.
- Request a quota increase if you exceed 20 federated credentials.

---

### GitHub App Installation Scope

The GitHub App must be installed on each target repository individually (or org-wide).

- New repos require manual App installation via GitHub UI.
- The `GITHUB_APP_INSTALLATION_ID` is per-org (or per-account) — not per-repo.
- If the App is uninstalled from a repo, agent runs for that repo will fail at the `gh repo clone` step.

**Mitigation**:
- Install the App org-wide if possible (covers all repos automatically).
- Document the App installation URL for your team.
- The container logs clearly indicate clone failures.

## 🟢 Minor Limitations

### Windows Development Quirks

`az acr build` with Docker output containing emoji/unicode characters causes encoding issues on Windows terminals. The `--no-logs` flag is needed to suppress streaming output.

```bash
# Windows workaround
az acr build \
  --registry <acr> \
  --image squad-agent:latest \
  --build-arg "BASE_ACR_HOST=<your-acr-login-server>/" \
  . \
  --no-logs
```

This only affects the build command — the built image works identically on all platforms.

---

### Squad State Merge Conflicts

The `.squad/` directory uses a `merge=union` git attribute driver for append-only files (history.md, decisions.md). This means concurrent PRs from different agents will auto-merge appended content.

**However**, structural edits (rewriting a section, reordering entries) can still conflict. This is rare because agents typically only append, but it can happen if:

- Two agents modify the same decision entry
- A human edits `.squad/` files while an agent PR is open
- The merge base is stale

**Mitigation**:
- Merge bot PRs promptly to reduce the window for conflicts.
- Agents only append to files — they don't rewrite existing content.
- If conflicts occur, they're standard git merge conflicts and can be resolved normally.

---

### Branch Naming Collisions

The branch naming pattern is `squad/{agent_type}/issue-{number}`. If two different queue messages specify the same agent type and issue number, the second container will detect the existing branch and exit cleanly.

This is **by design** (dedup check), but it means:
- Only the first container to claim an issue does the work.
- If the first container fails after creating the branch but before creating a PR, the issue is "stuck" (has a branch but no PR).

**Mitigation**:
- Delete the orphaned branch manually: `git push origin --delete squad/{agent}/issue-{N}`
- Remove the `squad:processing` label from the issue
- Re-label to retry

---

### PR Body Size Limit

GitHub limits PR bodies to ~65KB. The entrypoint truncates the PR body at 60KB if it exceeds this limit. Very large Copilot outputs or extensive diff stats may be cut off.

**Mitigation**:
- The truncation preserves the beginning of the PR body (summary, changes, commits) and adds a warning note.
- Full Copilot output is available in container logs (Log Analytics).

---

### Revision Stale Check

The `/squad revise` flow includes a stale SHA check: if the branch HEAD has moved since the revision was enqueued, the container aborts and comments a warning on the PR.

This prevents revisions from being applied to a branch that has changed (e.g., someone manually pushed a commit). But it also means:
- Force-pushing to a bot branch blocks revisions until `/squad revise` is re-triggered.
- Merging main into the bot branch changes HEAD and blocks revisions.

**Mitigation**:
- Don't manually push to bot branches — let the `/squad revise` flow handle iterations.
- If the stale check fires, just re-trigger `/squad revise`.
